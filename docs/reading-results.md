# 결과 읽는 법

네트워크 용어를 몰라도 결과 표를 읽을 수 있게 정리한 문서입니다. 실제 측정 결과 하나(7회 측정, 호스트만 가림)를 놓고 섹션별로 설명합니다.

## 먼저 알아 둘 다섯 가지

| 용어 | 뜻 |
| --- | --- |
| RTT (왕복) | 브라우저가 보낸 신호가 서버에 갔다가 응답이 돌아오는 한 번. 시간으로는 보통 수 ms~수백 ms이고, 사용자와 서버의 거리와 네트워크에 따라 다릅니다. |
| 세그먼트 | 서버가 데이터를 잘라 보내는 한 조각. 이 문서의 예시에서는 조각 하나에 1,238B가 실립니다. |
| cwnd | 서버가 응답을 기다리지 않고 **한 번에 보낼 수 있는 세그먼트 수**. 처음에는 작고, 왕복이 한 번 끝날 때마다 약 2배로 늘어납니다(슬로 스타트). |
| 라운드 | 서버가 cwnd만큼 한 번에 보낸 묶음. 라운드 1개 = 왕복 1번입니다. |
| handshake | 데이터를 주고받기 전에 연결을 맺는 과정(TCP 연결 + TLS 암호화 설정). 크기와 상관없이 왕복 2번이 듭니다. |

핵심은 하나입니다. 서버는 34개 → 68개 → 136개처럼 **라운드마다 2배씩** 보내므로, 파일 크기가 줄어도 필요한 라운드 수가 그대로면 도착 시각은 거의 같습니다.

## 1. 단계별 결과

| 단계 | 내용 | 전송량 | 결과 |
| --- | --- | --- | --- |
| handshake | TCP + TLS | 서버 TLS 응답 5세그먼트 | 프로토콜상 2 RTT |
| 1단계 | HTML | 5세그먼트 | 1 RTT |
| 2단계 (목표) | HTML에 명시된 같은 호스트 리소스(JS, CSS 등) | 182세그먼트 | 3 RTT |

페이지 로딩을 시간 순서로 나눈 표입니다.

- **handshake**: 연결을 맺는 2 RTT. 번들 크기로는 줄일 수 없는 고정 비용입니다.
- **1단계**: HTML을 받는 단계. 브라우저는 HTML을 읽어야 어떤 JS와 CSS가 필요한지 알 수 있어서, 이 단계가 끝나야 다음 요청을 보냅니다.
- **2단계 (목표)**: HTML에 적혀 있던 JS, CSS, 이미지를 받는 단계. 번들 최적화가 영향을 주는 곳이 여기라서 보통 이 단계가 "목표"입니다.

결과 칸이 "N RTT" 대신 **"대역폭 제한"**이면, 서버가 더 보낼 수 있는데 측정한 네트워크의 속도가 모자라 막혔다는 뜻입니다. 이 경우 왕복 횟수로는 설명할 수 없어서 RTT를 세지 않습니다.

## 2. RTT 예산

가장 중요한 표입니다.

| 단계 | 세그먼트 | 라운드(RTT, 회차별 실측) | 시작 cwnd(실측) | 1 RTT 줄이려면 | 다음 RTT까지 여유 |
| --- | --- | --- | --- | --- | --- |
| 1 | 5 | 1 (1, 1, 1, 1, 1, 1, 1) | 31 (관측한 cwnd 하한) | - | 31.7kB |
| 2 | 182 | 3~4 (4, 3, 3, 4, 3, 3, 3) | 34 (7회) | 권장 −100.0kB (최소 −97.6kB) | 68.3kB |

**2단계까지 총 RTT (handshake 2 포함): 6~7 (6: 5회, 7: 2회)**

| 열 | 읽는 법 |
| --- | --- |
| 세그먼트 | 이 단계에서 서버가 보낸 조각 수. 182개 × 1,238B ≈ 225kB입니다. |
| 라운드(RTT, 회차별 실측) | 맨 앞의 `3~4`는 회차별 값의 범위이고(모든 회차가 같으면 숫자 하나), 괄호 안은 7회 각각의 값입니다. 괄호 안 숫자가 비슷할수록 믿을 만한 결과입니다. |
| 시작 cwnd(실측) | 이 단계의 첫 라운드에 서버가 한 번에 보낸 세그먼트 수. 여기서 2배씩 늘어납니다. |
| 1 RTT 줄이려면 | 이만큼 줄여야 라운드가 하나 줄어듭니다. |
| 다음 RTT까지 여유 | 이만큼까지는 늘어나도 라운드 수가 그대로입니다. |

2단계 숫자가 어떻게 나왔는지 직접 계산해 보면 이렇습니다.

| 라운드 | 이번에 보내는 양 | 여기까지 누적 |
| --- | --- | --- |
| 1번째 | 34세그먼트 | 34 |
| 2번째 | 68세그먼트 | 102 |
| 3번째 | 136세그먼트 | 238 |

- 지금은 182세그먼트입니다. 102보다 많고 238보다 적으니 **3라운드**가 필요합니다.
- 2라운드에 끝내려면 102세그먼트 이하여야 합니다. 182 − 102 = 80세그먼트, 약 **98kB를 줄여야** 합니다.
- 3라운드의 한도는 238세그먼트입니다. 238 − 182 = 56세그먼트, 약 **68kB까지는 늘어도** 3라운드입니다.

그래서 이 페이지에서 번들을 30kB 줄이는 작업은 왕복 횟수를 바꾸지 못하고, 30kB짜리 라이브러리를 추가해도 왕복 횟수가 늘지 않습니다.

읽을 때 주의할 점

- **크기는 모두 압축 후 전송 크기**입니다(gzip, brotli 적용 후). 소스 코드나 빌드 결과물의 원본 크기가 아닙니다. 개발자 도구 Network 탭의 "전송됨(Transferred)" 크기와 비교하세요.
- **최소**는 경계에 딱 맞춘 값이고, **권장**은 압축률 오차를 감안해 조금 더 줄인 값입니다. 목표를 잡을 때는 권장값을 쓰세요.
- 1단계의 "1 RTT 줄이려면"이 `-`인 것은 이미 1 RTT라서 더 줄일 수 없다는 뜻입니다.
- **총 RTT**는 handshake 2 + 1단계 + 2단계입니다. 회차마다 따로 더하므로, 예시는 2 + 1 + 3 = 6(5회)과 2 + 1 + 4 = 7(2회)이라서 `6~7 (6: 5회, 7: 2회)`입니다.
- 라운드가 `3~4`처럼 1 차이 범위로 나오면 표 아래에 두 값이 함께 나옵니다. "다음 RTT까지 여유"(모델로 계산한 3라운드 한계까지 남은 양)와 "모든 회차를 3 RTT로 고정하려면" 줄일 양(4 RTT가 나온 회차의 마지막 라운드, 실측)입니다. 둘 다 작으면 크기가 경계에 걸쳐 있어서 실제 사용자도 3과 4를 오간다는 뜻입니다. 고정 감소량이 훨씬 크면 크기 때문이 아니라 그 회차들의 전송이 느렸던 것입니다.
- 라운드가 `2~4`처럼 2 이상 차이 나는 범위로 나오거나 "판정 불가"가 나오면 회차마다 결과가 너무 달랐다는 뜻입니다. 이때는 RTT 수를 믿지 말고, 측정 횟수를 늘려(9회) 다시 재세요. 이미 9회 이상 쟀다면 유선이나 다른 네트워크에서 다시 재세요.

## 3. RTT가 아닌 대기

| 구간 | 시간 | 의미 |
| --- | --- | --- |
| 서버 TLS 처리 | 약 22ms | 첫 요청까지 걸린 시간에서 TCP·TLS 왕복을 뺀 나머지 |
| 1단계 수신 후 다음 요청까지 | 약 8ms | HTML 파싱 등 브라우저 쪽 대기 |
| CDN MISS 등 긴 대기 | 1단계 83ms, 2단계 141ms 등 | 오리진에서 가져오는 시간. 라운드에서 제외 |
| 서버 대기 | 2단계 1ms, 11ms 등 | cwnd를 다 쓰기 전에 생긴 공백. 라운드에서 제외 |

왕복 횟수와 상관없이 흘러간 시간입니다. **번들 크기를 줄여도 이 시간은 줄지 않습니다.**

- **서버 TLS 처리**: 서버가 암호화 설정을 계산하는 시간.
- **1단계 수신 후 다음 요청까지**: 브라우저가 HTML을 읽고 다음 요청을 보내기까지의 시간.
- **CDN MISS**: CDN에 파일이 캐시되어 있지 않아 원본 서버에서 가져오느라 기다린 시간. 이 값이 크고 자주 나오면 번들 크기보다 CDN 캐시 설정(Cache-Control 등)을 먼저 봐야 합니다.
- **서버 대기**: 서버가 보낼 데이터를 준비하느라 멈춘 시간. 서버 렌더(SSR) 페이지의 1단계에서 크게 나오면 서버가 HTML을 만드는 시간이 길다는 뜻입니다.

시간 옆의 `≈ n RTT`는 그 시간이 왕복 몇 번에 해당하는지 환산한 참고값입니다. 총 RTT에는 더하지 않습니다.

## 4. 측정 조건

| 항목 | 값 |
| --- | --- |
| 측정 횟수 | 7회 |
| 전송 중 RTT (TCP timestamp) | 중앙값 6.8ms (회차별 5.7~8.0ms) |
| handshake RTT | 회차별 6.0~8.8ms |
| 세그먼트당 데이터 | 1238B (7/7회 일치) |
| 서버 TLS 응답 | 5세그먼트 (7/7회 일치) |
| 초기 cwnd 하한 (관측, 같은 호스트 회차 공유) | 26 |

이 결과를 얼마나 믿을 수 있는지 판단하는 표입니다.

- **전송 중 RTT**: 측정한 사람과 서버 사이의 왕복 1번에 걸린 시간. 예시는 6.8ms이므로 1 RTT를 줄이면 이 네트워크에서는 약 7ms가 줄어듭니다. 왕복이 100ms인 사용자라면 같은 1 RTT가 100ms입니다. **RTT 횟수는 사용자마다 비슷하지만 1 RTT의 시간은 사용자마다 다릅니다.**
- **handshake RTT**: 연결을 맺을 때 잰 왕복 시간. "2배 이상 흔들림"이라고 나오면 와이파이 등으로 측정 환경이 불안정했다는 뜻입니다.
- **세그먼트당 데이터**: 조각 하나에 실리는 양. `7/7회 일치`처럼 모든 회차가 같아야 정상입니다.
- **서버 TLS 응답**: 연결을 맺을 때 서버가 보낸 인증서 등의 조각 수.
- **초기 cwnd 하한**: 서버가 연결 직후 한 번에 보낼 수 있는 조각 수가 "적어도 이만큼"이라는 관측값. 교과서 값은 10인데 CDN은 더 큰 경우가 많습니다.

## 표 아래에 붙는 문구

| 문구 | 뜻 |
| --- | --- |
| 재전송 N회로 제외 | 패킷이 유실되어 다시 보낸 회차입니다. 유실이 생기면 서버가 보내는 양을 줄여서 계산의 전제가 깨지므로 뺐습니다. 한두 회차면 정상입니다. |
| 대역폭 제한, N/M회 | M회 중 N회가 네트워크 속도에 막혔습니다. 절반 이상이면 그 단계는 RTT로 세지 않습니다. |
| RTT 수 판정 불가 | 회차별 라운드 수가 2 이상 차이 나서 하나로 말할 수 없습니다. |
| LCP 리소스는 측정 범위 밖 | 화면에서 가장 큰 요소(LCP)가 JS 실행 뒤에 요청되어 이 측정에 잡히지 않았습니다. HTML에 preload를 걸면 범위 안으로 들어옵니다. |
| early flush | 브라우저가 HTML을 다 받기 전에 JS와 CSS를 요청했습니다. HTML이 초기 cwnd(약 14kB)보다 커서 여러 라운드로 오거나, 서버가 앞부분을 먼저 보내면 생깁니다. 서버가 그 요청을 받기 전에 이미 보낸 HTML은 1단계로 셉니다. 1단계가 HTML 크기보다 작으면, 그 차이(요청을 받은 뒤 보낸 HTML)가 2단계 전송량에 섞여 있습니다. |

## 결과를 보고 무엇을 할지

| 결과 | 판단 |
| --- | --- |
| "1 RTT 줄이려면"이 작다 (예: −5kB) | 조금만 줄이면 왕복이 하나 줄어듭니다. 할 만한 최적화입니다. |
| "1 RTT 줄이려면"이 크다 (예: −100kB) | 그만큼 줄일 방법이 없다면 번들 크기 최적화의 효과는 작습니다. 다른 곳(대기 시간, LCP 리소스의 요청 시점)을 보세요. |
| "다음 RTT까지 여유"가 크다 | 그 안에서는 라이브러리 추가나 코드 정리로 크기가 늘어도 왕복 횟수는 그대로입니다. |
| "다음 RTT까지 여유"가 작다 (예: 2kB) | 조금만 늘어도 왕복이 하나 늘어납니다. 크기가 늘어나는 변경을 조심해야 합니다. |
| "RTT가 아닌 대기"가 RTT 시간보다 훨씬 크다 | 번들보다 CDN 캐시나 서버 응답 시간이 병목입니다. |
| 대역폭 제한 | 이 네트워크에서는 왕복 횟수가 아니라 전체 크기에 비례해서 느려집니다. 줄인 만큼 빨라집니다. |
