# 검증 기록
스킬을 만들면서 판정 규칙을 고쳐 온 순서대로 적은 기록입니다. "블로그"는 이 스킬의 출발점이 된 글에서 Wireshark로 직접 센 캡처를 가리킵니다.

블로그 실측 캡처 두 개로 analyze.py → budget.py를 돌린 결과입니다. 블로그에서 Wireshark로 손으로 확인한 값과 같습니다.

| 항목 | 블로그 (손으로 확인) | 스크립트 |
| --- | --- | --- |
| 개선 전 MSS / 세그먼트당 데이터 | 1250 / 1238 | 1250 / 1238 |
| 개선 전 TLS 서버 응답 | 5세그먼트 | 5 |
| 개선 전 bundle.js 라운드 | 30 → 60 → 116 → 53 | 30 → 60 → 116 → 53 |
| 개선 전 CDN MISS 대기 | 228.5ms, 198.4ms | 228.5ms, 198.3ms |
| 개선 전 이미지 구간 | 대역폭 제한 (RTT 창마다 368/353/427) | bandwidth_limited, RTT 창별 세그먼트 수 출력 |
| 개선 후 2단계 라운드 | 35 → 70 → 36 | 35 → 70 → 36 |
| 개선 후 hero까지 RTT | 6 RTT | 6 RTT (--target-stage 2) |
| 개선 후 1 RTT 줄이려면 | 약 45kB | 권장 −46.3kB (최소 −43.9kB) (압축 후, 오버헤드 반영) |

추가로 확인한 것
- 수동 캡처용 회차 구간 분할(--window): 캡처 전체를 덮는 구간에서는 같은 결과, 벗어난 구간에서는 "연결 없음" 오류
- HTML 명시 리소스 추출(로컬 서버): preload·stylesheet·defer script는 포함. JS가 넣은 이미지, `loading=lazy` 이미지, icon, 다른 호스트 script는 제외
- 캡처가 잘려도 페이로드 길이를 IP 헤더로 계산(블로그 캡처의 전송량 172,832B 그대로)

당시 검증하지 못한 부분: 이 기록을 쓴 환경에는 tcpdump가 없어 실제 캡처 실행(자동·수동)은 돌려 보지 못했습니다. 이후 아래 기록들의 실측에서 확인했습니다.


## 판정 규칙 수정 (실측 피드백 반영)
실측에서 나온 오판 세 가지를 같은 패턴의 합성 캡처(`tests/run_cases.py`)로 재현하고 고쳤습니다. 단계별 라운드 세그먼트 수와 판정입니다.

| 패턴 | 수정 전 | 수정 후 |
| --- | --- | --- |
| SSR 서버 렌더 대기 (HTML 3세그먼트 → 80ms 대기 → 22세그먼트) | 1단계 대역폭 제한 | 1단계 1 RTT + 서버 대기 80ms |
| 페이싱 슬로 스타트 (RTT 창 47/66/71/137/52) | 2단계 대역폭 제한 | 2단계 5 RTT (페이싱) |
| 대역폭 제한 (RTT 창 30/36/36/36/36) | 대역폭 제한 | 대역폭 제한 (유지) |
| early flush (HTML 앞부분을 받자마자 하위 리소스 요청) | HTML과 리소스가 한 단계로 합쳐짐 | 1단계 / 2단계로 분리 |

블로그 캡처 두 개의 결과(30→60→116→53, 35→70→36, 개선 전 이미지 대역폭 제한)는 수정 후에도 같습니다.


## 전송 중 RTT로 라운드 구분 (와이파이 실측 피드백 반영)
와이파이 측정에서 handshake RTT가 20~67ms로 흔들리면서 RTT 수가 정답과 어긋났습니다. 두 가지를 고쳤습니다.

1. **라운드를 자르는 RTT**: handshake RTT 대신 TCP timestamp로 잰 전송 중 RTT의 최솟값을 씁니다.
2. **budget.py가 보고하는 RTT 수**: 시작 cwnd로 다시 계산한 값이 아니라 회차별로 실제 센 라운드 수(최빈값)를 보고합니다. 회차 간 불안정(라운드 수 2 이상 차이)과 속도 기반 전송 의심(첫 라운드가 RTT에 비례)은 자동으로 판정해 범위로 냅니다.

| 확인 | 결과 |
| --- | --- |
| 합성: handshake RTT 60ms, 실제 20ms, 페이싱 40/80/160/40 | 이전판 2라운드 [280, 40] → 수정판 4라운드 [40, 80, 160, 40] |
| 합성: 첫 라운드가 RTT에 비례하는 5회차 | "RTT 수 판정 불가, 2~3" + 상관 1.0 경고 |
| 블로그 개선 전 캡처 (정답 2단계 4 RTT, 총 7) | 4 RTT, 총 7. 전송 중 RTT 6.7ms (handshake 6.5ms) |
| 블로그 개선 후 캡처 (정답 2단계 3 RTT, 총 6) | 3 RTT, 총 6. 전송 중 RTT 6.9ms (handshake 8.4ms) |
| 기존 합성 4종 (서버 대기, 페이싱, 대역폭 제한, early flush) | 결과 동일 |


## ACK 인과관계로 라운드 구분 (와이파이 재분석 피드백 반영)
전송 중 RTT로 바꾼 뒤에도 시간 격자로 자르는 방식이라, 큐로 늘어난 RTT와 위상이 어긋나 조각 라운드가 생겼습니다(실측: 개선 전 [29, 43, 8, 99, 44, 19] → 6, 정답 4). 라운드를 TCP timestamp의 ACK 인과관계로 나누도록 바꿨습니다.

| 확인 | 시간 격자 (이전판) | ACK 인과관계 (수정판) |
| --- | --- | --- |
| 합성: 정답 4라운드, 전송 중 RTT 19→23ms, 공백 없는 페이싱 | 5라운드 [25, 45, 78, 72, 22] | 4라운드 [31, 60, 120, 31] |
| 합성: handshake RTT 부풂 / 페이싱 / 서버 대기 / early flush / 대역폭 제한 | 정답 | 정답 (라운드 크기는 ±2 차이) |
| 블로그 개선 전 캡처 (정답 4 RTT) | 30 → 60 → 116 → 53 | 30 → 60 → 116 → 53 |
| 블로그 개선 후 캡처 (정답 3 RTT) | 35 → 70 → 36 | 35 → 70 → 36 |
| 블로그 개선 전 이미지 구간 | 대역폭 제한 | 대역폭 제한 |


## cwnd 하한으로 라운드 합치기 (재분석 피드백 반영)
ACK 인과관계로 나누면 두 가지가 남았습니다: 페이싱 도중 새 ACK가 와서 생긴 1~2세그먼트 꼬리 라운드, 서버가 전송 중 멈춘 뒤 쪼개진 라운드. 측정 에이전트는 "마지막 라운드가 앞의 25% 미만이고 0.25 RTT 안이면 합치기"를 제안했지만, 이번 데이터에 맞춘 값이라 쓰지 않았습니다. 대신 슬로 스타트의 cwnd 하한(초기 10 + ACK된 세그먼트)으로 "cwnd가 나눈 라운드인가"를 판정하는 규칙 하나로 두 경우를 함께 처리했습니다. 새 상수는 없습니다.

`tests/test_real_rounds.py`: 실측 9회 + 블로그 2회의 라운드 크기로 11/11 정답 (개선 전 4, 개선 후 3).
같은 규칙으로 서버 유휴 시간도 ACK 기준으로 잽니다(블로그 개선 전 CDN MISS: 228.5ms 공백 − 최소 RTT = 221.8ms).


## 초기 cwnd 관측 하한, BBR 방식 대역폭 판정 (재분석 피드백 반영)
- **SSR 서버 렌더 HTML [2, 20]이 2 RTT로 세지던 문제**: 초기 cwnd 10 가정이 원인. "초기 cwnd ≥ 라운드 크기 − 그 전까지 받은 세그먼트"로 같은 연결의 관측값에서 하한을 올리도록 함(CloudFront 22~32). 새 상수 없음.
- **2.4GHz 대역폭 제한을 놓치던 문제, 5GHz CSR r3 오판**: "1.25배 2연속(라운드 크기)"을 BBR의 실제 판정(전송률 = 크기 ÷ max(도착 시간, RTT), 1.25배 3연속, tcp_bbr.c 상수)으로 교체.
  - 시도했다 버린 것: "라운드 도착 시간 ≥ RTT"(라운드 경계에 섞인 세그먼트 한두 개에 흔들림), "최대 전송률 × RTT = BDP"(수신 쪽에서 세그먼트가 뭉쳐 도착하면 전송률이 부풀어 블로그 이미지 구간을 놓침).
- `tests/test_real_rounds.py`: 실측·블로그 15건 통과(라운드 수 12건, 대역폭 판정 4건 중 2.4GHz 참, 블로그 2건·CSR r3 거짓).
- budget.py: 일부 회차만 대역폭 제한이면 그 회차를 빼고 계산, 한 라운드 단계의 시작 cwnd는 관측 하한 사용("다음 RTT까지 여유"가 나옴. 예: HTML은 30.5kB까지 늘어도 1 RTT).


## 회차 간 초기 cwnd 하한 공유 (재분석 피드백 반영)
- 같은 CloudFront 서버인데 회차마다 관측 하한이 10~25로 흔들려, SSR 1단계 [20, 4], [2, 20]이 2 RTT로 남았음. 초기 cwnd는 서버 설정이라 연결마다 같으므로, budget.py가 같은 호스트 회차들의 최댓값(23)을 공유해 다시 합침 → 1 RTT.
- 재전송이 있는 회차는 budget.py가 자동으로 제외(2.4GHz run1).
- 대역폭 제한 회차가 절반 이상이면 단계 전체를 대역폭 제한으로 판정(2.4GHz: 3/4회).
- CSR r3 [33, 37, 45, 125, 47]: 실측 도착 시간(18~26ms, RTT 19.86ms)으로 테스트를 바꿔도 대역폭 제한 아님. 라운드 수 5는 다른 4회(4)와 1 차이라 최빈값 4로 보고됨.
- `tests/test_real_rounds.py` 18건 통과.


## 예산 모델의 증가율을 2배로 (shout-ou.tz 교차 검증)
같은 서버의 세 페이지가 모두 4 RTT였는데, 측정 증가율(1.41~1.79배)로 계산하면 SSG는 5 RTT, CSR은 "여유 4.8kB"(SSG가 107kB 더 커도 4 RTT라 모순)가 나왔음. 슬로 스타트 이론값 2배로 바꾸자 다섯 대상(CSR, SSG, SSR, 글 개선 전·후) 모두 실측 RTT와 일치.


## 연결 선택·early flush 단계 처리 재검토 (규칙 변경 없음)
두 가지 변경 제안을 실측으로 확인했습니다. 둘 다 기존 규칙이 맞아서 바꾸지 않았습니다.

| 제안 | 확인한 데이터 | 결론 |
| --- | --- | --- |
| 연결을 "서버가 가장 많이 보낸 연결" 대신 "SYN이 가장 빠른 연결"로 고르기 | 블로그 개선 후 캡처에 같은 호스트(CloudFront)로 가는 연결이 2개 있음. SYN이 0.3ms 빠른 연결(서버 6,100B)은 TLS handshake만 하고 HTTP 요청 없이 40ms 만에 FIN·RST로 닫힘. 늦게 열린 연결이 HTML과 리소스 전부(339,064B)를 실음 | "SYN이 가장 빠른 연결"은 쓰지 않은 연결을 고름. 기존 규칙 유지 |
| early flush 회차를 HTML과 리소스를 합친 한 단계로 보기 | 합쳐서 처리하던 판에서는 v2 15회 중 6회가 한 단계로 묶여 목표 단계 번호가 달라졌고, 예산 계산에서 빠졌음(분리하게 된 이유). 유일한 실제 early flush(SSR r2)는 1단계 11.2kB < HTML 21.9kB이고, 2단계가 다른 회차보다 11.6kB 큼(HTML 나머지) | 브라우저는 HTML 앞부분을 받아야 리소스를 요청할 수 있으므로, 요청 왕복 두 번의 의존 관계는 early flush에서도 그대로임. 합치면 같은 페이지인데 회차마다 단계 번호가 달라짐. 분리 유지 |

v2 실측 25회는 모두 같은 호스트 후보 연결이 1개여서 연결 선택 규칙의 영향을 받지 않았습니다.

**남은 확인 거리 (합성으로만 재현, 규칙은 그대로 둠)**: 서버가 HTML 앞부분과 나머지를 같은 라운드에 보냈는데, 나머지가 리소스 요청보다 늦게 도착하는 경우입니다. 지금은 단계를 요청 시각으로 자르므로 HTML 나머지가 2단계 첫 라운드에 섞입니다. 초기 cwnd 30 서버, 리소스 53 → 97 합성에서 2단계가 3 RTT(정답 2), 초기 cwnd 하한이 48(실제 30)로 나왔습니다. budget.py는 회차 간 하한 최댓값을 공유하므로 다른 회차에도 영향을 줄 수 있습니다. 같은 모양의 보통 페이지(HTML 23세그먼트를 다 받고 요청)는 2 RTT, 하한 26으로 정답입니다. 실측 early flush 캡처(SSR r2)가 남아 있지 않아 확인하지 못했습니다. early flush 페이지를 다시 캡처해 확인한 뒤 고칩니다.
