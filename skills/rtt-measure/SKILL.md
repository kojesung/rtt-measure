# rtt-measure

배포된 페이지를 새 브라우저로 여러 번 열면서 패킷을 캡처하고, 그 결과로 아래를 계산한다.

- HTML과 HTML에 명시된 리소스를 받기까지 몇 RTT가 걸리는가
- 그 단계에서 **몇 kB를 줄이면 1 RTT가 줄어드는가 / 몇 kB까지 늘어도 괜찮은가**
- 실측 파라미터: 세그먼트당 데이터 크기(MSS − TCP 옵션), 서버 TLS 응답 세그먼트 수, 시작 cwnd와 증가율

계산은 반드시 `scripts/`의 스크립트로 한다. 패킷을 직접 세거나 암산하지 않는다. 같은 캡처에서는 항상 같은 결과가 나와야 하기 때문이다.

## 범위
- **측정 대상**: 서버가 보낸 HTML 원문에 명시된 같은 호스트의 리소스까지. stylesheet, script, modulepreload, preload, `loading=lazy`가 아닌 `<img>`가 해당된다. JS가 실행된 뒤 요청하는 리소스, API, 다른 호스트는 범위 밖이다.
- **결과의 의미**: 측정한 사람의 네트워크에서 배포된 서버 하나를 잰 값이다. 실행할 때마다 네트워크가 달라 결과가 흔들리므로 CI의 PR 비교에는 쓰지 않는다. 그 용도는 빌드 결과물로 이론값을 계산하는 도구가 맞고, 이 스킬의 실측값은 그런 도구의 설정을 보정하는 데 쓴다. 실제 사용자 전체의 로딩 시간은 RUM(web-vitals 수집, CrUX)으로만 알 수 있다.

## 절차

### 1. 측정 대상 받기 (필수)
시작하자마자 사용자에게 **배포된 HTTPS 주소와 측정할 경로 목록**을 받는다(예: `https://example.com/`, `/search`). 대화나 프로젝트에 이미 있으면 확인만 한다.
- 운영 주소 외에 Vercel preview나 스테이징 주소도 된다. 머지 전에 변경 효과를 재고 싶으면 그 주소를 받는다.
- 로컬 개발 서버(`localhost`)는 받지 않는다. RTT가 0에 가깝고 loopback MTU 때문에 MSS가 수만 바이트가 되어, 이 스킬이 구하는 값이 운영과 전혀 달라진다.

### 2. 준비: 임시 환경과 캡처 방식
의존성은 임시 폴더에만 설치하고, 끝나면 지운다. 셸 상태는 명령마다 초기화될 수 있으니 고정 경로를 쓴다.
```bash
RTT_TMP="${TMPDIR:-/tmp}/rtt-measure"
python3 -m venv "$RTT_TMP/venv" && "$RTT_TMP/venv/bin/pip" install -q dpkt playwright
PLAYWRIGHT_BROWSERS_PATH="$RTT_TMP/browsers" "$RTT_TMP/venv/bin/python" -m playwright install chromium
```
이후 스크립트는 `PLAYWRIGHT_BROWSERS_PATH="$RTT_TMP/browsers" "$RTT_TMP/venv/bin/python" scripts/...`로 실행한다.

패킷 캡처에는 관리자 권한이 필요하다. 비밀번호를 대신 입력하거나 요구하지 않는다. 먼저 자동 캡처가 되는지 확인한다.
```bash
"$RTT_TMP/venv/bin/python" scripts/capture.py --check --out rtt-runs
```
- **자동 캡처 가능**(종료 코드 0): 사용자가 캡처 권한을 이미 설정해 둔 경우다(macOS의 ChmodBPF, Linux의 `cap_net_raw` 등). 3단계에서 스크립트가 회차마다 직접 캡처한다.
- **자동 캡처 불가**: 수동 캡처로 진행한다. `--check`가 출력한 `sudo tcpdump ...` 명령을 사용자에게 주고, **본인 터미널에서 실행해 켜 둔 채로** 알려 달라고 요청한다. 권한을 영구로 설정하라고 요구하지 않는다. tcpdump가 없으면 설치 방법을 안내한다(macOS는 기본 포함).
- VPN이 켜져 있으면 MSS와 RTT가 달라진다. 실제 사용자 조건에 가깝게 재려면 끄도록 안내한다.

### 3. 측정
```bash
# 자동 캡처
… scripts/capture.py <URL> --runs 5 --warmup --out rtt-runs
# 수동 캡처: 사용자의 tcpdump가 켜져 있는 상태에서
… scripts/capture.py <URL> --runs 5 --warmup --out rtt-runs --no-capture
```
- 회차마다 새 브라우저를 띄우므로 브라우저 캐시가 없고 새 연결이다. QUIC을 꺼서 HTTP/2(TCP)로 연결된다.
- `--warmup`: CDN 캐시만 데운다(브라우저 캐시는 매번 비어 있다). CDN MISS는 오리진에서 파일을 가져오는 시간이라 크기나 RTT와 무관하고 측정마다 크게 흔들리기 때문이다. 그래도 MISS가 나면 분석에서 대기로 따로 표시된다.
- 회차마다 `run-N.json`이 남는다. HTML에 명시된 리소스(`declared`), 브라우저가 보낸 요청 묶음(`request_groups`), 회차 시작·끝 시각(`window`)이 들어 있다. 자동 캡처면 `run-N.pcap`도 남는다.
- 수동 캡처였다면 측정이 끝난 뒤 사용자에게 tcpdump를 Ctrl+C로 종료해 달라고 요청한다.
- HTTP/2가 아닌 프로토콜 경고가 나온 회차는 분석에서 뺀다.
- 와이파이에서는 RTT가 회차마다 크게 흔들릴 수 있다. 예산 결과에 "handshake RTT 2배 이상 흔들림"이나 "RTT 수를 하나로 말할 수 없음"이 나오면, 유선 연결로 다시 재거나 회차를 9회로 늘리자고 안내한다.

### 4. 분석
```bash
# 자동 캡처
for f in rtt-runs/run-*.pcap; do … scripts/analyze.py "$f" --host <호스트> > "${f%.pcap}.analysis.json"; done
# 수동 캡처: 파일 하나를 회차 시각으로 나눠 분석
for j in rtt-runs/run-*.json; do … scripts/analyze.py rtt-runs/capture.pcap --host <호스트> --window "$j" > "${j%.json}.analysis.json"; done
```
페이지 문서를 받은 연결을 찾아서 다음 값을 뽑는다.
- 전송 중 RTT, handshake RTT, MSS, 세그먼트당 데이터, 서버 TLS 세그먼트 수
- 요청 단계별 라운드(RTT) 구분과 라운드별 세그먼트 수
- RTT보다 훨씬 긴 대기(CDN MISS), 서버 대기, 대역폭 제한 여부

### 5. 검증 (계산 전에 반드시 확인)
스크립트가 판단할 수 없는 부분이다. 하나라도 어긋나면 그 회차를 빼거나 원인을 사용자에게 알린다.

1. **목표 단계 정하기**: `request_groups`에서 `declared_in_html: true`인 리소스가 몇 번째 묶음까지 있는지 본다. pcap의 단계와 순서대로 맞춰서, 그 묶음에 해당하는 단계 번호를 목표 단계로 정한다. 보통 2단계(1단계는 HTML)다.
   - 맞춰 볼 때는 각 단계의 전송량(`bytes`)이 묶음의 `encoded_bytes` 합에 오버헤드(약 1~3%)를 더한 정도인지 확인한다.
   - 명시 리소스가 여러 묶음에 흩어져 있으면 마지막 묶음까지를 목표로 한다.
2. **자동 처리되는 것**: 아래는 스크립트가 처리하므로 직접 판단하지 않고 그 결과를 따른다.
   - 연결 선택(analyze.py): 같은 호스트로 연결이 여러 개면 서버가 가장 많이 보낸 연결을 고른다. 브라우저가 연결을 두 개 열고 한쪽은 TLS만 마친 뒤 요청 없이 닫는 경우가 있기 때문이다(블로그 개선 후 캡처). `candidate_connections`가 여러 개여도 다시 고르지 않는다.
   - 재전송이 있는 회차는 패킷 손실로 cwnd가 줄어 슬로 스타트 전제가 깨지므로 자동으로 뺀다.
   - 초기 cwnd 하한은 같은 호스트의 모든 회차에서 관측한 최댓값을 공유해 라운드를 다시 합친다(초기 cwnd는 서버 설정이라 연결마다 같다). 회차 하나만으로는 증거가 부족해 하한이 낮게 잡힐 수 있기 때문이다.
   - 회차 간 일관성(라운드 수 차이, 첫 라운드와 RTT의 비례).
3. **대역폭 제한**: `bandwidth_limited`인 단계는 RTT로 세지 않는다. 근거로 `per_rtt_window`가 평평해진 구간을 함께 적는다.
4. **early flush**: `overlaps_previous`가 참인 단계는 브라우저가 HTML을 다 받기 전에 하위 리소스를 요청한 것이다(HTML이 초기 cwnd보다 커서 여러 라운드로 오거나, 서버가 앞부분을 먼저 보낸 경우). 서버가 그 요청을 받기 전에 보낸 HTML(요청 후 최소 RTT 안에 도착)은 analyze.py가 1단계로 센다. 그래서 1단계 전송량이 HTML 크기(`html_encoded_bytes`)보다 작게 남아 있으면, 서버가 요청을 받은 뒤에 보낸 HTML이 2단계 전송량에 섞여 있다고 보고에 적는다.

### 6. 예산 계산
```bash
… scripts/budget.py rtt-runs/run-*.analysis.json --target-stage <목표 단계>
# 크기를 바꾸면 어떻게 되는지: 단계=압축 후 전송 바이트
… scripts/budget.py rtt-runs/run-*.analysis.json --target-stage 2 --stage-bytes 2=125000
```
- **RTT 수는 회차별로 실제 센 라운드 수**(최빈값)다. 회차별 값이 함께 표시된다.
- 다음 경우 budget.py가 RTT 수를 범위로 내고 "1 RTT 줄이려면"을 "판정 불가"로 표시한다. 이때는 RTT 수를 단정하지 않고, 크기 비교만 확정적으로 보고한다.
  - 회차별 라운드 수가 2 이상 차이 남
  - 첫 라운드 크기가 회차별 RTT에 비례함: 서버가 일정한 속도로 보낸 데이터를 RTT 길이로 잘라 셌을 가능성
- "1 RTT 줄이려면"은 실측한 시작 cwnd(첫 라운드 세그먼트 수)에서 라운드마다 2배(슬로 스타트)로 계산한 모델 값이다. 측정한 라운드 크기 비율은 실제로 보낸 양이라 2보다 낮게 나와 쓰지 않는다. 모델의 라운드 수가 실측과 다르면 경고가 붙으니 참고로만 쓴다.
- 같은 서버의 여러 페이지를 쟀다면 교차 검증한다: 한 페이지의 시작 cwnd로 다른 페이지 크기의 RTT를 예측해 실측과 맞는지 본다. 맞지 않으면 "1 RTT 줄이려면"을 단정하지 않는다.
- 같은 서버의 여러 페이지를 쟀다면 예산은 **페이지별로** 따로 돌린다(한 번에 넘기면 단계가 섞인다). 대신 다른 페이지 결과를 `--init-cwnd-from`으로 넘겨 초기 cwnd 하한만 공유한다.
  ```bash
  … scripts/budget.py rtt-runs/ssr/run-*.analysis.json --target-stage 2 --init-cwnd-from rtt-runs/csr/run-*.analysis.json rtt-runs/ssg/run-*.analysis.json
  ```
- `--stage-bytes`에는 압축 후 크기를 넣는다. `run-N.json`의 `encodedBodySize`나 빌드가 만든 `.br` 크기를 쓴다. 소스 코드 크기가 아니다.

### 7. 보고
아래 네 섹션을 이 순서로, **모두 표로** 쓴다. 표 아래에는 근거나 예외만 짧은 목록으로 덧붙인다. 2~4는 budget.py 출력의 표를 그대로 옮기고, 1은 `run-N.json`과 분석 결과로 채운다.

**1. 단계별 결과**

| 단계 | 내용 | 전송량 | 결과 |
| --- | --- | --- | --- |
| handshake | TCP + TLS | 서버 TLS 응답 5세그먼트 | 프로토콜상 2 RTT |
| 1단계 | HTML(압축 후 746B) | 5세그먼트 | 1 RTT |
| 2단계 (목표) | HTML에 명시된 같은 호스트 리소스 7개, 압축 후 338kB | 278세그먼트, 343kB | 3 RTT 또는 "대역폭 제한, 4/4회" |

- 목표 단계 리소스가 많으면 큰 순서로 3~4개와 나머지 합계를 쓴다. 회차마다 한 묶음으로 요청됐는지도 적는다.
- 대역폭 제한이면 근거(`per_rtt_window`가 두 배로 늘지 않음)를 적고, 총 RTT는 내지 않는다.

**2. RTT 예산**: budget.py의 표 (1 RTT 줄이려면 권장값·최소값, 다음 RTT까지 여유). 최소는 1 RTT가 줄어드는 경계까지 줄여야 하는 양이고, 권장은 압축률과 오버헤드 오차를 감안해 조금 더 줄인 양이다. 표 아래에 이 설명을 그대로 옮긴다.

**3. RTT가 아닌 대기**: budget.py의 표 (구간 | 시간 | 의미). 서버 TLS 처리, 단계 사이 브라우저 대기, CDN MISS, 서버 대기. 없으면 "없음"으로 행을 남긴다.

**4. 측정 조건**: budget.py의 표에 측정한 네트워크(VPN 여부), 프로토콜, 대역폭 제한 구간 여부를 행으로 더한다.

`lcp_in_scope`가 false면 표 아래에 한 줄 덧붙인다: "LCP 리소스는 HTML 이후에 요청되어 이 측정 범위 밖입니다. HTML에 preload를 걸면 범위 안으로 들어옵니다."

표현 규칙:
- RTT 횟수와 ms를 섞어 더하지 않는다. "≈ n RTT"는 참고값으로만 쓴다.
- "몇 kB 줄이면"은 항상 **압축 후 전송 크기** 기준이라고 밝힌다.
- 한 번 측정한 값이나 회차마다 다른 값은 단정하지 않는다.
- 측정자 네트워크의 값을 모든 사용자의 값처럼 쓰지 않는다. RTT 횟수는 서버의 cwnd·MSS가 주로 정해서 ms보다 일반화하기 쉽다. 다만 대역폭이 좁은 사용자는 더 일찍 대역폭 제한 구간에 들어간다는 조건을 붙인다.

### 8. 정리
측정이 끝나면 임시 환경(`$RTT_TMP`, 브라우저 포함 수백 MB)을 지울지 사용자에게 묻고, 동의하면 지운다. 측정 결과(`rtt-runs/`)는 남긴다.

### 9. (선택) 이론 계산 도구 보정
빌드 결과물로 RTT를 계산하는 도구를 함께 쓴다면, 기본 가정(MSS 1,460, 초기 cwnd 10 등)을 실측값으로 바꿔 줄 수 있다.
- 세그먼트당 데이터 = `payload_per_segment` (예: MSS 1250 − timestamp 12 = 1238)
- TLS 응답 세그먼트 = `tls_server_segments`
- 초기 cwnd = `init_cwnd_lower_bound` (관측한 하한)

## 해석 참고
- **첫 라운드가 초기 cwnd 10보다 큰 이유**: 서버의 TLS 응답과 HTML 응답이 ACK되면서 cwnd가 이미 늘었고, 서버의 초기 cwnd 자체가 10보다 클 수도 있다. 둘을 패킷만으로 정확히 나눌 수는 없다. 그래서 예산은 "초기 cwnd"를 추정하지 않고 **실측한 첫 라운드 크기**로 계산한다.
- **MSS가 1,460이 아닌 이유**: 서버와 경로가 정한 MSS에서 TCP timestamp 옵션(12바이트)이 빠진다. 예: MSS 1250 → 데이터 1238.
- **증가율이 2배가 아닌 경우**: BBR을 쓰는 서버(CloudFront 등)는 측정한 대역폭으로 속도를 정해서 정확히 2배가 아닐 수 있다. 실측 증가율을 쓴다.
- **1단계에 서버 대기가 보이는 경우**: CDN이 HTML을 오리진에서 가져오느라 늦게 보낸 것이다. cwnd 하한보다 적게 보낸 뒤의 공백은 라운드로 세지 않는다.
- **라운드는 시간이 아니라 ACK 인과관계로 나눈다**: 서버 세그먼트의 TCP timestamp(TSecr)는 서버가 그 세그먼트를 보낼 때 받아 둔 가장 최근 클라이언트 ACK의 TSval이다. 라운드의 첫 세그먼트를 확인한 ACK를 서버가 되돌려 주기 시작하면 다음 라운드로 센다(BBR이 라운드를 세는 방식과 같다). 시간 격자로 자르면 페이싱이나 큐로 늘어난 RTT 때문에 경계가 어긋나 조각 라운드가 생기는데, 이 방식은 그 영향을 받지 않는다(`round_method: ack`). timestamp가 없는 연결(Windows 클라이언트 등)만 시간 공백 방식으로 대체하고(`round_method: time`), 이때는 결과를 덜 믿는다고 보고에 적는다.
- **전송 중 RTT**: handshake RTT(SYN→SYN+ACK) 한 번은 와이파이 절전 해제 등으로 실제보다 몇 배 길게 잡힐 수 있다. 그래서 TCP timestamp로 모은 전송 중 RTT 표본의 최솟값을 쓴다. 이 값은 요청 묶음 구분과 "≈ n RTT" 환산에 쓰이고, 라운드 수 자체에는 영향을 주지 않는다.
- **서버 대기는 RTT 판정에서 뺀다**: 서버 렌더, CDN MISS, 오리진 대기로 생긴 공백은 줄일 수 없는 서버 쪽 시간이다. analyze.py는 이 공백을 라운드 시간과 RTT 창 계산에서 빼므로, 대기 때문에 대역폭 제한으로 판정되지 않는다. 대기는 "RTT가 아닌 대기" 표에만 남고 총 RTT와 "1 RTT 줄이려면"에는 들어가지 않는다.
- **대역폭 제한은 BBR과 같은 방식으로 판정한다**: 라운드별 전송률 = 라운드 크기 ÷ max(라운드 도착에 걸린 시간, 최소 RTT). 대역폭에 여유가 있으면 라운드가 RTT 안에 도착해 전송률이 라운드마다 커지고, 막히면 병목 대역폭에서 평평해진다. 전송률이 지금까지 최대의 1.25배 이상 커지지 않는 라운드가 3번 연속 나오면 그 첫 라운드부터 대역폭 제한이다. 1.25배와 3회는 Linux BBR(tcp_bbr.c)이 STARTUP을 끝내는 기준과 같은 값이다. 대역폭 제한 회차가 절반 미만이면 그 회차를 빼고 나머지로 RTT를 계산하고, 절반 이상이면 단계 전체를 대역폭 제한으로 본다. 어느 쪽이든 몇 회였는지 적는다.
- **cwnd 때문에 나뉜 라운드만 센다**: 슬로 스타트에서 cwnd는 "초기 cwnd + 지금까지 ACK된 세그먼트"보다 작을 수 없다. 연속한 두 라운드를 합쳐도 앞 라운드 시작 시점의 이 하한 안에 들어가면, cwnd가 나눈 게 아니라 페이싱 도중 새 ACK가 와서 TSecr만 바뀐 꼬리이거나 서버가 데이터를 늦게 준 것이므로 합친다.
- **초기 cwnd 하한은 관측으로 올린다**: 어떤 라운드도 그 시점 cwnd를 넘을 수 없으므로 "초기 cwnd ≥ 라운드 크기 − 그 전까지 받은 세그먼트"다. 연결 안 모든 라운드에서 이 값의 최댓값을 하한으로 쓴다(최소 RFC 6928의 10). CloudFront처럼 초기 cwnd가 10보다 큰 서버에서는 하한이 20~30대로 올라가, 서버 렌더 HTML처럼 앞부분을 먼저 보내고 기다린 경우도 1 라운드로 센다. 결과의 `init_cwnd_lower_bound`가 이 값이다. 이 규칙들은 슬로 스타트가 이어진다는 전제에 기대므로, 패킷 손실로 슬로 스타트가 일찍 끝난 회차(재전송 있음)는 뺀다.
- **서버 유휴 시간은 ACK로 잰다**: 첫 응답이 "요청 + 최소 RTT"보다 늦게 온 만큼, 그리고 클라이언트가 받은 데이터를 모두 ACK했는데도 다음 데이터가 "ACK + 최소 RTT"보다 늦게 온 만큼을 서버 유휴(보낼 데이터가 없던 시간)로 기록한다. 라운드 수에는 영향을 주지 않는다.
- **오버헤드**: 압축된 본문에 TLS 레코드와 HTTP/2 프레임 헤더가 붙어 1~3% 커진다. budget.py는 1.015배로 계산한다.
